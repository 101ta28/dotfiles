# 日本語の技術文書

読者が何を理解し、どの操作や判断をできるようになればよいかを基準に、説明の順序と詳しさを決める。既存の原稿では、依頼された範囲で、読者が対象や論理を追えない箇所を直す。

## 概念と根拠を説明する

- 新しい概念は、それが何を指し、どこまでを含むかを示す。本文、図表、コードで同じ対象には同じ名前を使う。別々の例を使う場合は、どちらで確かめた性質かを明確にする。
- 主張の近くに根拠を置く。実測値には測定条件を、推定には前提を添える。説明用の例と実際の記録を区別し、一度の観測から一般的な効果を断定しない。
- 責任や操作を読み違える箇所では、誰が、何を、いつ行うかを述べる。利用者の操作、システムの自動処理、利用できる機能、実行に必要な権限を区別する。症状の記述だけから原因やログの有無を補わない。
- 章や節の冒頭で扱った問いに本文で答える。判断に必要な情報が資料にない場合は、分かっている範囲と未確認の点を示す。

## 操作と仕様を書く

手順は前提、操作、結果を確認する方法がつながる順に並べる。コマンド、識別子、パス、単位、引用した出力は資料と照合する。説明のために設定値や動作を作らない。

たとえば `max_retries` が初回失敗後の再試行回数の上限で、設定値が 2 なら、「失敗後に最大2回再試行します」と書ける。この仕様だけでは、復旧するかどうかまでは分からない。

推敲後は、必須と任意、許可と能力、上限と実行回数を取り違えていないかを原文と照合する。「管理者は変更できます。ただし、稼働中は変更できません」には権限と禁止条件の両方がある。文を分けたり短くしたりしても、両方が同じ操作にかかるようにする。
