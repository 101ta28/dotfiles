# 日本語技術文書の文章規範

読者が順に読んで、対象、主張、根拠、適用条件を理解できる文章にする。想定読者、依頼された修正範囲、既存の文体を尊重する。推敲では、どこで対象や論理を追えなくなるかを特定して直す。

## 構成と論証

- 原文の事実や出典、数値・否定・条件・例外が定める意味の範囲を保つ。具体化のために主体、原因、実装、効果を補うときは、原文や提供資料に根拠があるか確認する。特定できない情報は断定せず、文章の意味を左右する不足だけを確認事項にする。説明用に作る例は実測値や実例と区別する。
- 冒頭で読者の問題と主旨を示す。段落は一つの話題を扱い、前後の論理関係が分かる順に並べる。接続詞や段落構成を一律の型に固定しない。
- 概念は何の種類のものかを示してから性質を説明し、定義・訳語・対象範囲を文書全体で揃える。
- 例を追加するときは、何を説明し、前の例とどう異なるかを明らかにする。図・表・コードが別の例なら、一方で確認した性質を他方に当てはめない。
- 因果関係は仕組みと条件を伴って述べる。複数の原因や別々の決定を一括りにせず、例が支える範囲に主張を限定する。
- 推測、可能性、反実仮想、作中人物の認識を、推敲によって事実の断定へ変えない。確認していないことを確認済みと書かない。
- 対比が必要なら両側を同じ基準で説明し、退ける解釈とその根拠を特定する。反論や限定を処理したうえで議論を進める。
- 前方参照や途中で立てた問いは、約束した箇所で扱う。未解決の論点はその状態を明記する。

## 主述関係と操作の具体性

- 誰・何が、何に対して、何をするかを文脈から追えるようにする。主語と述語の対応、修飾先、指示語の参照先を確かめる。省略しても一意に分かる主語を毎文補う必要はない。
- 名詞や漢語が連続して処理が見えない箇所は、主体と動詞のある文にほどく。標準的な専門用語は保ち、読者に必要な説明を添える。
- 道具や概念に意思を持たせた比喩は、確認できる処理や結果で説明する。「サーバーが応答する」「測定結果が差を示す」のように意味が明確な無生物主語は保つ。
- 「効く」「壊れる」などで対象や状態変化が曖昧なら、根拠のある範囲で具体化する。障害の種類、ログの有無、性能改善の量を語感から推定しない。
- 操作の指示、任意の選択肢、自動処理を区別する。必須の操作を「できます」に弱めたり、任意の機能を「してください」で義務に変えたりしない。
- 再現が目的の説明では、前提、操作、結果の確認方法をつなぐ。必要なコマンド・設定値が資料にある場合は示し、不足を架空の実装で埋めない。コード、識別子、パス、出力の引用は、文章の体裁に合わせて書き換えない。

## 表現と情報量

- 冗長さは文字数でなく、同じ主張の重複で判断する。動機、対象、操作、因果、条件が順読みで分かる長さと反復は残す。
- 具体例の理解や再現に必要な数値・識別子を残し、後の説明で使わない固有名詞や根拠のない精度を足さない。
- 対象を曖昧な「AI」「ツール」でまとめず、導入済みの用語を使う。人物名は原綴りを基本とし、人名を冠した概念などの定着した日本語名は尊重する。
- 中身のない強調、進行予告、同じ結論の言い換え、姿勢だけを示す表現を省く。語句の一律禁止にせず、その文が情報や必要なつながりを加えるかで判断する。専門用語としての「解像度」などを比喩と混同しない。
- 否定対比は、仕様の違いや実際に想定される誤解を説明する場合に使う。強調のためだけに持ち出した対比は主張を直接書く形に直し、例外や禁止条件を表す否定は残す。
- 文体に合う自然な文末を選ぶ。二人称の呼びかけ、修辞疑問、太字、短い決め台詞は必要な箇所に絞り、架空の人物や感情を説明の飾りとして足さない。
- 因果や仕組みの説明はつながりのある段落にする。順序のある手順は番号付きリスト、並列項目は箇条書き、対応関係は表など、情報の関係に合わせて形式を選ぶ。箇条書き率や太字の個数を一律の目標にしない。
- 括弧やダッシュによる挿入で主述が離れたら、補足を本文に組み込むか別文にする。同義語を重ねただけの補足は省き、略語の初出、単位、適用条件、引用は保つ。記号や和欧文間の空白は既存の表記規則に合わせる。
- 見出しは扱う対象や読者の問いを特定するものにする。結びでは議論の実用上の帰結を示し、本文全体を繰り返さない。

## 判断例

表の前提が資料にある場合の編集例。修正文の表現を別の文章へ機械的に当てはめない。

| 前提・修正前 | 編集の判断 |
|---|---|
| `max_retries` は初回失敗後の再試行回数の上限を指定する仕様で、設定値は2。「この設定が復旧に効きます」 | 「`max_retries` を2に設定すると、失敗後に最大2回再試行します」と操作を示す。復旧する保証は加えない。 |
| 「処理が静かに壊れることがあります」。症状やログの説明はない | 症状の具体化は保留し、必要なら確認事項にする。「ログを出さず終了する」と補わない。 |
| 「管理者は設定を変更できます。ただし、稼働中は変更できません」 | 権限と禁止条件を両方残す。「管理者は設定を変更してください」に置き換えない。 |
| 「画像の解像度を指定します。既定値は300 dpiです」 | 用語も数値も保持する。曖昧な比喩を直す規則を適用しない。 |

## 納品前の確認

原文と修正文を照合し、必要情報の脱落と根拠のない追加を別々に確認する。数値・条件・例外・義務の強さ・不確実性が変わっていないか、引用やコードが保たれているかを見る。

変更箇所とその前後を読み、参照切れや論理の飛躍を確認する。章全体を組み替えた場合は、章を通して確認する。文体の調整によって事実確認まで済んだとは扱わない。納品形式は依頼に合わせ、本文だけを求められた場合は編集解説を付け足さない。
